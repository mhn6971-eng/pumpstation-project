# دفترچهٔ راهبری و بازیابی — نسخه ۱.۳
**سامانه پایش ایستگاه پمپاژ زیرزمینی — تونل انتقال آب گلاب**

این سند برای کسی نوشته شده که «فردا صبح سامانه بالا نیامد» — هر سناریو قدم‌به‌قدم آمده است.
هیچ قدمی «حذف فایل» یا «نصب دوباره از صفر» را بدون گرفتن نسخهٔ پشتیبان پیشنهاد نمی‌کند.

---

## ۰) یک نگاه سریع

| موضوع | مسیر / فرمان |
|---|---|
| اجرا | `npm run preview` (دیتابیس را مهاجرت می‌دهد و سرور را روی پورت ۳۰۰۰ بالا می‌آورد) |
| اجرای تولیدی | `npm run build` سپس `npm start` |
| سلامت | `GET /api/health` (عمومی) و `GET /api/health?full=1` با حساب ادمین |
| بک‌آپ دستی | تب ادمین → «بک‌آپ کامل فوری» یا اکشن `backup.create` |
| بک‌آپ خودکار | هر روز ۳ تا ۵ بامداد، در `.data/backups` (نگه‌داری ۳۰ نسخه) |
| بایگانی سالانه | اکشن `data.archive` — انتقال داده‌های قدیمی‌تر از ۳ سال + فایل فشرده |
| تعمیر دیتابیس | `npm run doctor` و برای بازسازی `node scripts/doctor.mjs --repair` |
| خروجی اکسل | `/api/export?table=motor&from=1404/01/01&to=1404/12/29` (ادمین) |

---

## ۱) نصب از صفر (رایانهٔ جدید یا ویندوز عوض شده)

1. **Node.js 22** را نصب کنید (نسخهٔ LTS).
2. پوشهٔ برنامه را کپی کنید (همان پوشهٔ `pumpstation-v1.2`).
3. در ترمینال همان پوشه:
   ```bash
   npm ci
   npm run db:init      # ساخت جدول‌ها
   npm start            # یا برای اجرای توسعه: npm run preview
   ```
4. مرورگر: `http://localhost:3000` — ورود با PIN شیفت یا ادمین.

> اگر تنها یک نسخهٔ بک‌آپ دارید، پیش از هر کار دیگری:
> `node scripts/doctor.mjs --restore <نام فایل>` و بعد سامانه را بالا بیاورید.

---

## ۲) چک‌لیست روزانه (۲ دقیقه)

1. `/api/health` → `ok: true`
2. تب ادمین → کارت «امنیت، سلامت و نگه‌داری»:
   - فضای دیسک آزاد > ۱ گیگابایت
   - «بک‌آپ فایلی — آخرین … ساعت پیش» کمتر از ۳۰ ساعت
   - «زنجیرهٔ دفتر فعالیت: سالم»
   - تعداد «خطای ۲۴ ساعت» صفر یا کم
3. فهرست دستگاه‌های واردشده: نشست ناشناس نباشد.

هر هشدار نارنجی که دیدید، در انتهای همین سند راه‌حل دارد.

---

## ۳) بک‌آپ: چه چیزی، کجا، چند وقت

| نوع | محل | تکرار | کاربرد |
|---|---|---|---|
| فایلی (JSON + چک‌سام) | `.data/backups` | روزانه ۳–۵ بامداد + دستی | بازیابی کامل پس از خرابی |
| داخلی (جدول `backups`) | داخل دیتابیس | دستی و خودکار پیش از هر بازیابی | برگشت سریع |
| بایگانی سرد (jsonl.gz) | `.data/backups/archive` | سالانه | نگه‌داری بلندمدت مستقل از دیتابیس |

**قاعدهٔ طلایی:** بک‌آپ روی همان دیسک برنامه، «بک‌آپ» نیست.
روزانه/هفتگی پوشهٔ `.data/backups` را روی حافظهٔ بیرونی (فلش، NAS یا فضای ابری) کپی کنید.
مثلاً در ویندوز با Task Scheduler:
```
robocopy D:\pumpstation\.data\backups  E:\backup-pumpstation  /MIR /R:2 /W:5
```

### آزمون بازیابی (ماهی یک‌بار، ۵ دقیقه)
تب ادمین → بخش «بک‌آپ‌های روی دیسک» → دکمهٔ **آزمون** روی آخرین فایل.
اگر «فایل سالم و قابل بازیابی است» آمد، بک‌آپ واقعاً قابل استفاده است.

---

## ۴) سناریوهای خرابی

### ۴-۱) قطع برق / خاموشی ناگهانی
دیتابیس PGlite با `fsync` واقعی کار می‌کند؛ پس از روشن شدن، سامانه باید بدون کار خاصی بالا بیاید.
اگر بالا نیامد:
```bash
npm run doctor              # گزارش می‌دهد
node scripts/doctor.mjs --repair   # بازسازی از آخرین بک‌آپ
```

### ۴-۲) «دیتابیس باز نمی‌شود» یا جدول‌ها ناقص‌اند
1. سامانه را ببندید (مهم: دو برنامه نباید هم‌زمان دیتابیس را باز کنند).
2. `npm run doctor` → اگر «خراب» گفت:
3. `node scripts/doctor.mjs --repair`
   - پوشهٔ خراب به `.data/pglite.broken-<تاریخ>` منتقل می‌شود (پاک نمی‌شود).
   - دیتابیس تازه ساخته و مهاجرت‌ها اجرا می‌شود.
   - آخرین بک‌آپ فایلی بازگردانده و شمارش ردیف‌ها تطبیق داده می‌شود.

### ۴-۳) کاربر داده‌ای را اشتباه پاک کرد
- تجهیزات: تب ادمین → «سطل بازیافت» → «بازگرداندن».
- کاتالوگ: فایل حذف‌شده در `files/catalogs/trash` است.
- بقیهٔ موارد: اکشن `backup.restore` روی بک‌آپ قبل از حادثه.

### ۴-۴) ادمین PIN را فراموش کرده / همه قفل شده‌اند
- قفل ورود خودکار پس از ۵ یا ۲۰ خطا بسته می‌شود؛ ۱۰ دقیقه صبر یا از حساب ادمین:
  اکشن `admin.unlock` با `{ "key": "all" }`.
- اگر PIN ادمین فراموش شده و کس دیگری دسترسی ندارد:
  ```bash
  node scripts/reset-admin-pin.mjs        # PIN ادمین را به 9999 برمی‌گرداند
  ```
  (پس از اجرا، بلافاصله از داخل سامانه PIN را عوض کنید.)

### ۴-۵) رایانه سوخته و فقط هارد/بک‌آپ مانده
1. نصب تازه طبق بخش ۱ (بدون ورود به سامانه).
2. `node scripts/doctor.mjs --restore <آخرین فایل بک‌آپ>`
3. سامانه را بالا بیاورید و صحت داده‌ها را ببینید.

### ۴-۶) سرور واقعی PostgreSQL (جدا از PGlite)
- در `src/db/index.ts` بلوک `pg` موجود است؛ `DATABASE_URL` را تنظیم و همان بلوک را فعال کنید.
- پشتیبان‌گیری: `pg_dump -Fc pumpstation > pumpstation.dump` در Task Scheduler روزانه.
- بازیابی: `pg_restore -d pumpstation --clean pumpstation.dump`.

---

## ۵) افزایش حجم داده (بعد از ۲–۳ سال)

- وضعیت را ببینید: تب ادمین → «بایگانی داده‌ها»، یا `data.stats`.
- بایگانی: `data.archive` با `{ "years": 3 }`.
  - دادهٔ قدیمی به جدول `*_archive` منتقل و یک فایل `readings-*.jsonl.gz` ساخته می‌شود.
  - نمودارها همچنان همهٔ سال‌ها را می‌بینند (نمای ترکیبی).
- بهینه‌سازی: `data.optimize` (VACUUM ANALYZE + پاک‌سازی نشست‌های کهنه).

---

## ۶) به‌روزرسانی نسخه

1. بک‌آپ فایلی بگیرید (دکمهٔ ادمین).
2. کد جدید را جایگزین کنید (پوشهٔ `.data` و `files` را دست نزنید).
3. `npm ci` سپس `npm run db:init` سپس `npm run build` و `npm start`.
4. `npm test` (یا حداقل `npm run test:audit`) را روی نسخهٔ آزمایشی اجرا کنید.

---

## ۷) مانیتورینگ بیرونی (اختیاری ولی توصیه‌شده)

هر ۵ دقیقه:
```bash
curl -fsS http://<server>:3000/api/health || echo "PUMPSTATION DOWN"
```
اگر `ok:false` بود یا پاسخ نیامد، هشدار بفرستید (تلگرام/بله/ایمیل).

---

## ۸) پرسش‌های پرتکرار

**چرا خروجی PDF گاهی کند است؟** گزارش از دیتابیس ساخته می‌شود؛ در حجم بالا از فیلتر تاریخ استفاده کنید.
**چرا دو تب با هم هماهنگ‌اند؟** سامانه با `BroadcastChannel` تب‌های همان دستگاه را همگام می‌کند و هر ۶۰ ثانیه تازه می‌شود.
**اگر اینترنت قطع شود چه می‌شود؟** ثبت‌ها در حافظهٔ مرورگر صف می‌شوند و با «کلید یکتا» پس از وصل شدن ارسال می‌شوند؛ سرور تکراری‌ها را دوباره اعمال نمی‌کند.
**چرا بعد از ۱۲ ساعت باید دوباره وارد شوم؟** عمر نشست برابر یک شیفت است؛ امنیت ایستگاه.
